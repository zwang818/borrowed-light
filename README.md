# 借光

> 借着一盏灯，记住走过的路，带你看看外面的世界。

一款使用 Godot 开发的 2D 俯视角像素剧情闯关游戏，也是四人游戏开发课程小组项目。

玩家操控一台小机器人，进入机械神兽内部，与维护系统对抗，营救创造自己的神明意识。机器人通过照明探索未知区域，将走过的地方保存为记忆，并使用简单武器完成战斗与闯关。

## 获取与运行

1. 接受仓库协作邀请。
2. 使用 GitHub Desktop 克隆本仓库到自己的电脑。
3. 在 Godot 项目管理器中选择导入，打开仓库根目录的 `project.godot`。
4. 等待素材导入完成，进入编辑器。
5. 按 F5 运行项目；若尚未指定主场景，先选择约定的 `main.tscn`。

遇到问题时，在任务看板记录：复现步骤、预期结果、实际结果，以及 Godot 报错原文或截图。

## 计划玩法

- 固定顺序的短关卡，目标完整流程约 10–15 分钟。
- 照明探索：未知区域被黑暗遮挡，探索过的地形保存在空间记忆中。
- 简单战斗：两种武器、两类普通敌人、一名最终 Boss。
- 维修终端、门禁和少量周期机关。
- 场景触发的短对话与完整营救故事。
- 少量场景中的维护协议通行，不以频繁切换形态作为核心战斗机制。

以上为设计范围，不表示功能已经完成。故事的详细设定与隐藏内容另行管理。

## 建议目录

目录随实际需求建立。Git 不记录空目录，第一版不必预建全部文件夹。

```text
res://
├── project.godot
├── README.md
├── scenes/
│   ├── main.tscn
│   ├── player/
│   ├── weapons/
│   ├── enemies/
│   ├── levels/
│   ├── interactables/
│   └── ui/
├── scripts/
├── assets/
│   ├── sprites/
│   ├── audio/
│   └── fonts/
├── data/
├── tests/              # 可手动运行的功能测试场景
└── docs/               # 项目约定、素材来源、设计说明
```

脚本可与对应场景放在同一模块目录，也可使用 `scripts/`；由小组确定后保持一致。文件和目录优先使用小写英文与下划线，例如 `player.tscn`、`cleaner_enemy.gd`。

## 协作流程

1. 开始任务前，确认工作区的修改已保存或提交，获取最新 `main`。
2. 从最新主分支创建任务分支，例如 `feat/player-movement`、`feat/cleaner-attack`、`fix/door-collision`。
3. 每个任务分支集中完成一个可检查的小功能，避免混入无关改动。
4. 保存全部场景，在本地运行相关测试场景与主场景。
5. 提交并上传修改，发起 Pull Request（合并请求）。
6. 由另一位成员查看改动、按说明验证，再合并到 `main`。
7. 合并后通知相关成员更新；原作者跟进由本次改动引入的问题。

`main` 应保持可启动、可运行。正式玩法接入后，还应能完成当前已支持的基本流程。

提交说明写清具体变化，例如：`feat: 增加玩家基础移动`、`fix: 修复清扫者死亡后继续攻击`。

## 场景与共享文件

- 玩家、敌人、武器、门、终端等尽量保存为独立场景，在关卡中实例化组合。
- 开始修改其他成员正在编辑的场景前，先在小组中协调。
- 修改 `project.godot`、输入映射、Autoload、碰撞层、公共 TileSet 或主场景前，先协调时间与影响。
- 移动、重命名资源优先在 Godot 文件系统面板操作，完成后检查引用。
- 遇到冲突时，对照双方修改共同处理，保留需要的内容；不要直接覆盖另一人的成果。
- 模块需要共用的函数、信号、分组和数据名称，先讨论再记录到 `docs/`，修改后通知受影响成员。

## 任务与完成标准

任务看板采用：待做 → 进行中 → 待检查 → 已完成。

每项任务写清负责人、目标、依赖和验收方法。一个功能完成时应满足：

- 已在公共项目中接通，另一位成员能按说明运行。
- 正常操作和相关失败／重试流程检查通过。
- 没有新增阻断当前流程的错误或缺失资源。
- 涉及公共接口和操作变化时，说明已更新。
- 使用 AI 生成的代码，提交者理解其作用，并已亲自运行验证。

## 版本管理注意事项

- 使用 Godot 生成的 `.gitignore` 与 `.gitattributes`，忽略 `.godot/` 缓存。
- 提交 `project.godot`、脚本、场景、源素材和必要的资源配置。
- 如果当前版本生成 `.uid` 文件，应随对应资源提交，不要将 `*.uid` 加入忽略规则。
- 素材旁的 `.import` 配置与 `.godot/` 中的导入缓存不同，不要笼统忽略所有 `.import` 文件。
- 打包产物放到单独的构建目录，并加入忽略规则。
- 如果后续采用 Git LFS，在提交大型素材前统一配置，并确保所有成员安装、使用一致。
- 外部素材记录来源和许可，便于课程交付时整理署名。
