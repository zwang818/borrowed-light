## 场景结构和接口边界

- `Floors`：17块普通可编辑地板。`Walls`：58段实体墙／设备基座，复用第一关组件。
- `Reservations`：安全区、通电地板、协议区、图纸／管道区、候选检查点的可视预留。脚本只绘制矩形，无 Area2D、伤害、计时或状态行为；`logic_implemented = false`。
- `Markers`：18个唯一稳定 ID；类型继续使用公共 map_marker.gd 的既有枚举。两哨机、两清扫者都只是位置标记。
- `Rooms`：4个逻辑房间候选多边形，只作分组，不代表实际视野，也不能整区揭图；候选矩形包含非行走空间，正式可见性必须结合地板和墙体。
- `RouteWaypoints`：主路、返回近路、记录支路与管道落点支路，可拖动参考点；运行时不生成或重造地形。
- 所有容器变换保持默认；标记位置由 `map.to_local(marker.global_position)` 读取。

新角色语义记录为标记 metadata，不扩展公共枚举：协议终端 `role=protocol`、图纸点 `role=blueprint`、候选检查点使用 spawn 类型和 `role=checkpoint_candidate`、近路门 `role=shortcut`／`unlock_side=east`。这些是 A 给 C 的候选接入字段，不宣称已有消费者。

出口 `p2_exit_to_thorax` 当前关联同地图的预览落点 `p2_thorax_landing / p2_thorax_entry`，以便独立验证引用；正式胸腔加载成功的提交由 C 后续接入。第一关既有 `p1_landing_01 / p1_landing_entry` 等稳定 ID 未改；C 后续从现有落点转入第二关的 `p2_spine_entry`，不能仅靠同名猜测自动接通。
