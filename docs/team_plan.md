## 2. 文件归属与不重叠原则

以下为按需创建的约定路径，除已有主场景外，不表示文件已经存在。不为符合目录表预建大量空文件夹。

| 文件或目录 | 唯一主维护人 | 使用方式 |
| --- | --- | --- |
| `scenes/levels/`，环境图片与 TileSet | A | 维护地图布局场景、墙体、遮光结构和摆放标记；其他人实例化使用 |
| `scenes/player/`、`scenes/weapons/`、`scenes/enemies/`、`scenes/bosses/` | B | 场景与专用脚本放一起；其他人调用公开接口 |
| `scenes/interactables/`、`scenes/hazards/` | C | 提供门、终端、拾取物、机关等可复用对象 |
| `scenes/runtime/`、`scripts/exploration/`、对局状态脚本 | C | 组装地图、玩家、UI，维护可见性、房间生命周期和重试 |
| `scenes/ui/`、`assets/fonts/`、`assets/audio/`、对话与日志数据 | D | UI 和声音消费真实事件，不直接改其他模块内部数据 |
| `project.godot`、`scenes/main.tscn` | C | 统一维护输入动作、碰撞层、必要全局配置与主入口 |
| `tests/manual/a_map/`、`b_combat/`、`c_progress/`、`d_ui/` | 对应成员 | 各自独立测试，不修改别人的测试场景 |
| 本分工表及公共接口约定 | C 汇总 | 成员提出更新，由 C 统一整理，避免同时编辑 |

具体资源目录沿用实际工程约定；首次落地时记录，不同时维护两套 `data/` 和 `resources/`。

### 地图场景与运行场景分开

- A 的地图提供地形、碰撞、遮光结构、区域数据，以及玩家、敌人、门和终端的摆放位置与配置。
- C 的运行场景实例化地图，再根据配置接入 B 的玩家和敌人、C 的交互对象、D 的 UI。
- 物件实例可以由 A 在编辑器摆放，也可以由运行场景按标记生成；**同一物件只用一种方式**，不能生成两份。
- P1 采用“地图摆放标记，运行场景按标记生成”，让 A 在其他模块未完成时也能提交可打开的地图。
- C 调整连接关系时改自己的运行脚本，不进入 A 的地图修改布局；地图位置不合适由 A 调整。

例如：C 负责门能否打开、如何恢复；A 负责门放在哪里；D 负责交互提示怎么显示。三个人不共同编辑门的内部场景。

**开发不必等正式地图，集成必须等待真实接口。** “用假数据跑通”只能证明模块可演示，不能算第一次可玩集成通过。

测试替身只能实现必要接口，不复制一整套正式系统。不能通过“引用失败就默认成功”“永远可见”等回退让正式入口假装正常；正式入口缺模块时应明确报告错误。

## 4. 当前阶段目标：P1 最小可玩样板

**玩家能够进入灰盒房间，取得脉冲枪，探索并战斗，操作终端开门亮灯，抵达相邻落点；也能够受伤死亡、正确重试。**

可玩流程：

> 启动 → 看见操作提示 → 移动探索 → 必经路取得脉冲枪 → 与一台哨机战斗 → 阅读一条短记录 → 操作终端 → 门开灯亮 → 进入相邻落点 → 显示“样板完成”，可返回检查进度。

“样板完成”只表示本测试流程结束，不是正式剧情结局。终端不增加“击杀全部敌人才可用”的新规则；可通过布局安排战斗体验，不擅自增加强制清场门禁。

| P1 必须包含 | P1 暂不制作 |
| --- | --- |
| 一个灰盒战斗房间、一个可返回的相邻落点 | 五个正式场景的完整美术 |
| 玩家、脉冲枪、一个固定哨机 | 散射工具、清扫者、Boss |
| 受伤、死亡、入口重试 | 完整维修点系统 |
| 主角照明、墙体遮挡、探索记忆 | 精细迷雾边缘与复杂灯光效果 |
| 一个终端、一扇门、一组可恢复固定灯 | 协议体验和周期机关 |
| 简单耐久 HUD、交互提示、暂停和重试界面 | 完整剧情演出与多条日志内容 |
| 简易记忆界面：地图和日志两页，一条短记录 | 跨程序完整存档 |
| 基础射击、受伤、预警、交互音效 | 完整配乐与精细混音 |

本阶段优先验证 Bible 中 COMBAT、VISION、STATE 和相关 QA；暂不涉及的玩法仍属于项目最终交付范围。

| 玩家恢复入口 | B | C | 由 C 传入合法位置、检查点耐久和保留的武器集合；B 清理自己的临时战斗状态 |

## 8. 提交、合并与启动顺序

“第一次可玩合并”指 **P1 集成验收节点**，不是要求全组只进行一次 Git 合并。底层配置和可独立运行的小模块应先陆续合入，最终由集成 PR 接通主入口。

1. **先合公共约定与必要配置。** C 维护 `project.godot`，其他人拉取相同基线。
2. **四人并行提交模块。** 每个模块 PR 附独立测试入口；不能引用只存在于自己电脑或别人尚未合并分支的文件。
3. **分步接通。** A 地图 + B 玩家先可走；接 C 交互与视野；接 B 哨机；接 D 界面；最后验证重试与跨房间状态。依赖模块未合入时，集成 PR 明确标出依赖，不假装已可运行。
4. **C 提交集成 PR。** 主入口使用真实模块，测试替身留在各自测试目录。至少一位非作者成员按验收脚本检查。
5. **检查通过再标 P1 完成。** 四人拉取相同提交后启动；如失败，定位到模块负责人修复，不由 C 越界重写所有模块。

独立运行：在 Godot 打开对应测试场景运行当前场景（通常 F6）。整体运行：运行项目（通常 F5），仍使用 `scenes/main.tscn`。A 的腹腔独立预览现已存在；主入口未接入地图，F5 仍运行标题。其他成员的测试入口以实际文件与验证记录为准。

每次 PR 至少填写：

```text
任务 ID：
负责人：
修改文件：
运行入口：
操作步骤与预期结果：
实际验证结果：
依赖的已合并 PR / 提交：
公共接口或共享配置是否变化：
未完成项 / 需队友处理事项：
```

提交前检查：无丢失资源和本机绝对路径；必要 UID、资源与脚本一起提交；不提交 `.godot/`；不混入其他成员的未完成改动。遵循已有 PR 流程，不直接提交到 `main`。
